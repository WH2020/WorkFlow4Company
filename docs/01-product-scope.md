# 产品范围、成功指标与验收标准

## 1. 产品定位

Agent4Company 是面向公司整体管理的本地优先桌面平台。它帮助公司负责人、业务负责人和执行人员在一个中文工作台中发起任务、处理审批、查看项目与知识、进入业务域并追溯审计记录。

平台的核心产品原则是：公司级轻本体保持稳定，业务规则由插件提供。销售管理是首个接入域，但客户、机会、销售行动等概念不得进入平台核心数据模型或成为公司首页的固定经营指标。

## 2. 目标用户与场景

| 用户 | 典型场景 | 第一阶段支持程度 |
| --- | --- | --- |
| 公司负责人/经营管理者 | 查看跨域任务、审批和运行状态，发起经营分析 | 本机单人身份可验证 |
| 业务域负责人 | 进入本域、发起流程、批准结构化写入 | 销售域可验证 |
| 项目负责人 | 在项目范围组织任务、文件和业务对象链接 | 信息架构与能力契约已接入，写入延期 |
| 执行人员 | 发起任务、补充上下文、查看进度 | 统一任务入口可验证，多人身份延期 |
| 审批人 | 核对作用域、载荷和影响后批准或驳回 | 本地管理员角色可验证 |
| 审计/合规人员 | 只读追溯任务、节点、审批和结果 | 本地审计列表可验证，专用只读身份延期 |
| 平台管理员 | 管理插件、模型、搜索、角色与运行状态 | 状态展示可验证，配置写入延期 |

## 3. 要解决的问题与证据

已证实的源项目问题：

- 产品包、默认 Profile、桌面常量、工作台导航和定时任务以销售总监为中心。
- 共享周报和部分输出适配器通过销售 Profile 白名单选择能力，阻碍第二业务域接入。
- 源任务、审批、审计、用户文件和配置位于运行目录，不能进入新项目。
- 源插件的 category 固定为 `shared/market/product`，不适合作为公司级任意业务域契约。

本阶段不使用虚构市场数据或业务收益。产品价值先通过可验证的工程独立性、治理完整性和桌面可用性证明。

## 4. 产品目标

1. 公司工作台在没有销售域时仍能启动并展示共享能力。
2. 新业务域可以通过清单和工作流接入，不需要修改平台核心代码。
3. 结构化写入不能绕过审批；任务、审批与审计使用同一事实来源。
4. 新仓库不继承源 Git 或任何真实业务/用户/运行数据。
5. Windows 用户可以通过独立桌面窗口启动，不以普通浏览器作为正式产品入口。

## 5. 功能优先级

### 必须实现

- 公司级默认 Profile、信息架构和中文桌面工作台。
- 插件发现、依赖版本、权限和 DAG 校验。
- 统一任务、审批、审计运行时与本地持久化。
- 共享能力插件契约：模型、搜索、知识、项目、文件、PPT、调度。
- 销售域插件和一个完整的“读取 → 分析 → 审批 → 写入意图 → 验证”流程。
- Windows 安装、启动、构建、自检和基本测试。
- 产品、架构、迁移、安装、开发和验收文档。

### 建议实现

- 销售域启停配置和只读历史任务展示。
- 公司级只读域摘要贡献接口。
- 操作者与审批人职责分离。
- 文件上传的大小、类型、路径和符号链接门禁。
- 调度器创建标准 DAG 任务的集成测试。

### 可以延期

- 企业 SSO/AD/LDAP、云端多用户同步和生产级多租户。
- 财务、人力、产品、交付等真实业务域。
- 远程插件市场、在线安装、移动端和分布式调度。
- 真实业务数据迁移、数据仓库和 BI。
- 签名安装器、自动升级和正式发布流水线。

### 明确不做

- 不把销售仪表盘改名后继续作为公司平台本体。
- 不让模型自行审批，不让调度器越过审批。
- 不安装 `@juicesharp/rpiv-todo` 或维护第二套任务事实源。
- 不启用 ReqGuard，也不创建 `docs/reqguard`。
- 不恢复源 WeFlow、微信、个人邮箱或用户绑定集成。
- 不迁移源 Git、真实数据、配置、凭据、日志、数据库、输入输出和安装产物。
- 未获授权前不创建或绑定远端仓库。

## 6. 主流程与异常流程

主流程：

```text
启动桌面应用
→ 公司总览
→ 选择业务域工作流
→ 统一任务运行时按 DAG 推进
→ 结构化写入前生成冻结载荷与哈希
→ 审批中心人工批准或驳回
→ 经批准的节点继续
→ 验证节点完成
→ 审计记录全过程
```

异常流程：

- 模型或搜索未配置：明确显示“尚未配置/本地模式”，不阻止工作台启动。
- 插件缺失、依赖不兼容、DAG 有环或权限越界：启动验证失败并给出具体插件/节点。
- 任务版本或审批载荷变化：旧审批失效，禁止写入。
- 非审批角色操作：返回权限错误并保留任务等待状态。
- 端口被占用：桌面壳拒绝接管未知服务并给出中文错误。
- 销售域缺失：公司核心插件仍可加载，业务域列表为空。

## 7. 成功指标

| 指标 | 第一阶段目标 | 验证方式 |
| --- | --- | --- |
| 独立仓库 | 新仓库无源历史、无远端 | `git log`、`git remote -v` |
| 插件治理 | 所有清单、依赖、权限、DAG 通过校验 | Python/TypeScript 双实现测试 |
| 审批完整性 | 100% 结构化写入具有唯一直接审批前驱 | 正向与绕过审批负向测试 |
| 审批防替换 | payload/版本不一致时 100% 拒绝 | 载荷篡改单元测试 |
| 核心独立性 | 移除销售插件后平台注册仍可启动 | 临时无销售插件测试 |
| 销售域接入 | 空数据流程到达审批并在批准后完成 | CLI、运行时和 HTTP 集成测试 |
| 数据洁净度 | 无真实数据、数据库、日志、凭据和安装产物被提交 | Git 跟踪路径与敏感模式扫描 |
| 中文桌面路线 | Tauri 窗口加载本机中文工作台 | 构建、`--self-test`、人工窗口检查 |

## 8. 第一阶段验收标准

- `company-manager` 默认 Profile 的 `enabled_domains` 为空。
- `domain.sales` 由插件目录发现；公司核心不导入销售存储。
- 销售流程具有五个确定节点和一个直接审批门禁。
- 审批记录至少包含公司、域、项目、操作者、角色、策略/版本、任务/节点、payload hash、storage binding、expected version、decision 与时间。
- HTTP 服务只绑定回环地址，POST 缺少会话令牌时拒绝。
- Tauri 产品名、identifier、窗口标题、端口和日志目录均为公司平台命名。
- 所有必须文档存在且不建立独立需求门禁目录。
- 实际执行的测试、构建和未覆盖项记录在 `docs/05-acceptance.md`。
